# 私人AI创作助手 · 产品整合设计方案

> 版本：V1.0 | 2026-07-31
> 角色：产品整合Agent（AI产品经理 × 前端架构师 × 系统设计负责人）
> 性质：**纯设计方案，不含代码**。落地时以本方案为骨架，逐模块小步实现。

---

## 〇、设计原则（工作规则的落实）

| # | 原则 | 在本方案中的体现 |
|---|------|----------------|
| 1 | 不推翻已有Agent设计 | 内容生成Agent / 执行发布Agent 的设计文档全部保留，仅补充接口定义 |
| 2 | 不重新设计内容生成逻辑 | `generator.py` 现有引擎（离线模板+API润色）直接复用，零改动 |
| 3 | 保持模块独立 | 三个模块只通过"素材包"这一个标准数据接口通信 |
| 4 | 统一数据契约 | `publish_package.json`（素材包）作为模块间唯一数据桥梁 |
| 5 | 个人开发者可落地 | 单进程 Python 模块化，不上微服务、不引入消息队列 |
| 6 | 稳定 > 简洁 > 性能 > 新技术 | 优先复用 V1.5 已验证的能力，再谈重构 |

> 一句话：**不改引擎，只加"契约 + 编排 + 页面"。**

## 一、产品定位

### 1.1 一句话定位

> 一个 20 岁自学 AI 的抖音创作者，只输入**「本周主题 + 3张照片」**，
> 就能得到完整可发布的图文内容包（文案 / 代码标签 / 封面 / BGM），
> 人工审核后，自动填充到抖音发布页。

### 1.2 用户与场景

| 项 | 内容 |
|----|------|
| 目标用户 | 20岁，正在自学AI/编程，用短视频记录成长过程 |
| 内容形式 | 抖音图文（封面图 + 代码图 + 生活照） |
| 核心场景 | 每周五花 3 分钟，把一周的学习成果变成一条内容 |
| 真实输入 | 主题 + 三张照片：**① 标题封面 ② 代码学习执行图 ③ 生活照** |
| 真实痛点 | 想文案、打代码标签、配BGM、排版发布，每周耗时数小时 |

### 1.3 产品承诺

**做（交付价值）：**

- 输入主题+照片 → 自动产出标题、正文、标签、封面文字
- 代码截图自动打「代码含义」标签，观众一眼看懂
- 按内容情绪 + 场景 + 账号定位推荐 BGM
- 自动整理素材包，人工审核后自动填充抖音发布页

**不做（边界清晰）：**

- ❌ 自动点击「发布」按钮（安全原则：人永远是最终负责人）
- ❌ 自动登录 / 自动扫码（用户手动登录，Agent从已登录态开始）
- ❌ 自动下载音乐（第一版只推荐，不负责下载）
- ❌ 多平台 / 定时发布 / 多账号（V2 及以后再说）

### 1.4 核心价值指标

| 指标 | 现状（人工） | 目标（整合后） |
|------|------------|--------------|
| 单期创作耗时 | 3-5 小时 | **3 分钟** |
| 文案/标签/BGM 一致性 | 依赖灵感 | 稳定模板 + 人设红线 |
| 发布出错率 | 手动操作易漏 | 发布前自检清单 |

## 二、用户流程

### 2.1 每周操作全景（用户视角）

```
周一   确定本周学习主题
周二–周四  学习 + 写代码，随手拍 3 张照片
         ↓
周五   【打开应用 → 3 分钟完成创作】
         │
         ① 输入：主题 + 上传照片
         ② 点「生成」→ 文案/标签/封面/BGM 全部产出
         ③ 结果页检查 → 可编辑修改
         ④ 点「审核通过」→ 自动填充抖音发布页
         ⑤ 浏览器里最后看一眼 → 手动点发布
         ↓
周日   看数据，把值得记的写进《爆款分析库》
```

```

                │                        │

★ 智能体永远不会自动发布。
★ 自动填充后，浏览器停在发布确认页，由用户点最终「发布」。
```

### 3.2 与当前 V1.5 的关系（不推翻，只解耦）

| 现状（V1.5） | 问题 | 整合方案 |
|-------------|------|---------|
| 三块能力都在 `main.py` 里以函数/标签页形式耦合 | 模块边界模糊，改一处影响全局 | 抽「编排层」，引擎保持原样 |
| BGM 推荐内嵌在生成流程中 | 无法独立使用、无法替换 | 提供标准输入输出接口，仍是同一批代码 |
| 发布记录写 Excel，无展示页 | 用户看不到历史全貌 | 历史页只读读取，不改变写入方式 |
| 页面 = 一个窗口 4 个标签页 | 流程感弱 | 按 6 页面梳理导航，保留现有标签页作为结果页内分区 |

**关键决策：整合不动引擎代码，只加一层"契约 + 编排 + 页面"。</br>优先保证「现在就能用」不退化，再逐步解耦。**

### 3.3 技术栈分层

┌─────────────────────────────────────────────┐

### 4.3 模块间通信方式

| 通信 | 方式 | 触发 |
|------|------|------|
| 内容生成 → 素材包 | 写入 `output/第N周_日期/publish_package.json` | 用户点「生成」 |
| 音乐推荐 ← 素材包 | 从素材包读取 `analysis` 字段，回写 `bgm_candidates` | 生成流程内自动 / 用户手动刷新 |
| 素材包 → 执行发布 | 读取最新素材包 | 用户点「审核通过」 |
| 执行发布 → 历史 | 写 `publish_report.json` + 追加 `发布记录.xlsx` | 发布填充完成 |

**低耦合保证：**

- 内容生成引擎不调用音乐模块内部函数，只写素材包
- 音乐模块只读 `analysis` 字段，不依赖内容引擎内部逻辑
- 发布引擎只读素材包，不认识 UI
- 任一模块可单独替换（如换更好的音乐推荐服务）而不影响其他模块

### 4.4 边界定义（各模块明确不做的事）

| 模块 | 不做 |
|------|------|
| 内容生成引擎 | 不做自动发布、不做音乐下载、不做平台登录 |
| 音乐推荐模块 | 不下载/不存储音乐文件（第一版）；只输出推荐信息 |
| 执行发布引擎 | 不点最终「发布」、不处理登录扫码、不做多平台 |
| 主控Agent | 不做业务决策，只做流程编排和数据校验 |

## 六、数据流设计

### 6.1 单一数据源：素材包 `publish_package.json`

所有模块围绕同一个 JSON 流转，**它是模块间唯一的握手协议**。

```
            ┌─────────────────────────────────────────────┐
            │               publish_package.json          │
            │   (output/第30周_20260731/ 目录下)            │
            │                                             │
            │  content    ── 标题/正文/标签/封面文字        │
            │  analysis   ── 情绪/场景/内容类型/账号定位    │◄── 音乐模块输入
            │  images     ── 图片绝对路径 + 类型 + 标签文字  │
            │  bgm        ── 最终选定 BGM                  │◄── 音乐模块输出
            │  publish_config ── 平台/模式/开关             │
            │  output_dir ── 成品包目录                    │
            └─────────────────────────────────────────────┘
```

### 6.2 各模块接口定义

#### 接口 A：内容生成引擎 → 素材包（已实现，保留）

输入（用户表单 + 内部 JSON）：

```json
{
  "week": 30,
  "theme": "用AI三小时学完Python基础",
  "learning_content": "列表推导式、函数定义、文件读写",
  "completed": "写了一个自动整理桌面的脚本",
  "difficulties": "装饰器还没理解",
  "images": {
    "code_screenshots": [".../code1.jpg", ".../code2.jpg"],
    "life_photos": [".../life1.jpg"]
  }
}
```

输出（素材包，现有 `content`/`images` 字段不变）：

```json
{
  "content": {
    "title": "我用AI三小时学完了Python基础",
    "body": "20岁。\n我开始认真学习AI。\n第30周。…",
    "tags": ["AI学习", "Python入门"],
    "cover_text": "20岁学AI\n第30周"
  },
  "images": [
    {"file": ".../封面图.png", "type": "cover"},
    {"file": ".../打标签代码图.png", "type": "code_with_tag", "tag_text": "列表推导式一行搞定循环"},
    {"file": ".../生活照.png", "type": "lifestyle"}
  ]
}
```

#### 接口 B：音乐推荐模块 输入/输出（需接口化，逻辑已实现）

**输入**：从素材包 `analysis` 派生，独立成一个数据对象（低耦合关键）：

```json
{
  "emotion": "温暖励志",                    // 内容情绪
  "scene": ["学习", "代码", "生活"],        // 图片场景
  "content_type": "image_text",            // 内容类型
  "theme": "用AI三小时学完Python基础",       // 主题关键词
  "account_positioning": "20岁AI自学记录"    // 账号定位（来自个人知识库）
}
```

**输出**：写回素材包 `bgm_candidates`，并支持选择一首写回 `content.bgm`：

```json
{
  "bgm_candidates": [
    {
      "name": "起风了",
      "artist": "买辣椒也用券",
      "search_keyword": "起风了 纯音乐",
      "reason": "温暖励志，适合成长记录类内容",
      "clip_suggestion": "副歌部分，约30-60秒处",
      "score": 92,
      "mood_tags": ["温暖", "励志", "成长"]
    },
    { "...": "..." },
    { "...": "..." }
  ]
}
```

**独立性保证**：音乐模块只依赖 `music_db.json` + `analysis` 字段，
不认识内容生成引擎内部任何实现；即使换掉内容引擎，音乐模块照常工作。

#### 接口 C：执行发布引擎 输入/输出（已实现，保留）

输入 = 素材包 `publish_package.json`（校验图片存在 / 标题≤55字 / 标签≤5个）

```json
{
  "content": {"title": "...", "body": "...", "tags": [...], "bgm": {...}},
  "images": [{"file": "...", "type": "..."}],
  "publish_config": {"platform": "douyin", "publish_mode": "manual_confirm"}
}
```

输出 = `publish_report_{时间戳}.json`（状态 / 执行日志 / 自检结果 / 截图路径）

```json
{
  "status": "pending_confirm",
  "self_check_result": {"all_passed": true, "checks": [...]},
  "execution_log": {"steps": [...], "duration_seconds": 202},
  "screenshot_path": ".../发布预览_xxx.png",
  "warnings": []
}
```

## 七、技术方案

### 7.1 技术选型（个人开发者导向）

| 层 | 技术 | 说明 |
|----|------|------|
| 语言 | Python 3.10+ | 与现有引擎统一 |
| 前端（V1.5/MVP） | **tkinter**（现状保留） | 零重写，马上能用 |
| 前端（V2 可选） | FastAPI + 原生 HTML/JS，或 Streamlit | 迁移时页面逻辑复用 |
| 编排层 | Python 模块（主控Agent / 页面控制器） | 新增薄层，纯函数式编排 |
| 内容引擎 | `generator.py` | 不动 |
| 音乐模块 | `music_recommender/` | 接口化，不动核心算法 |
| 发布引擎 | `publisher.py`（Playwright） | 不动 |
| 存储 | JSON + xlsx + 文件系统 | 不引入数据库 |
| AI 服务 | DeepSeek（API润色，可选）｜ 离线规则引擎 | 失败自动回退离线 |

### 7.2 前端方案

- **MVP 原则**：继续用 tkinter。整合只做「新增两个页面 + 音乐区域独立」，不重写窗口。
- **页面逻辑层**：每个页面封装为独立的控制器对象（Controller），
  - 输入：页面数据对象（Pydantic / dataclass）
  - 输出：页面状态 + 触发动作
  - 好处：V2 换 Web 时，控制器与数据对象直接复用，只换渲染层。
- **状态管理**：
  - 全局状态：`draft.json`（草稿自动保存）+ 内存中的"当前素材包"
  - 页面间传递：只通过素材包对象，页面不直接互相读内部状态
  - 会话恢复：重开应用 → 读取 `draft.json` 恢复全部内容

### 7.3 后端方案

- **MVP**：无 HTTP 服务。单进程 Python，编排层直接函数调用三引擎。
- **API 设计（V2 可选，现在定契约）**：

```
POST /api/content/generate      # 内容生成
POST /api/music/recommend       # 音乐推荐
POST /api/publish/execute       # 发布执行
GET  /api/history               # 历史记录
GET  /api/history/{week}        # 某期素材包
```

- **Agent 调用方式**：MVP = 进程内函数调用；V2 = 主控Agent通过 FastAPI 调度。
  两者共用同一套数据对象，因此切换成本低。
- **数据存储**：见 6.4。MVP 不引入数据库。

### 7.5 关键技术决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 是否重写 UI | 否，保留 tkinter | 不破坏已有流程，MVP 快速交付 |
| 是否引入数据库 | 否 | 数据量小，文件系统够用；SQLite V2 再说 |
| 是否引入 FastAPI | MVP 否，V2 可 | 个人开发者运维成本；契约先定好 |
| 素材包如何统一 | `package.py` 单一模型 | 三模块读写同一份校验过的 JSON |
| 情绪/场景从哪来 | 内容引擎产出 `analysis` 字段 | 复用现有生成结果，不新增一次 AI 调用 |
| 失败兜底 | 音乐模块失败 → 空推荐 + 默认曲目；发布失败 → 三级降级 + 手动指南 | 沿用现有容错策略 |

## 八、MVP 开发路线

### 8.1 三阶段总览

```
第一阶段（MVP）  打通「主题+照片 → 审核 → 填充发布」闭环
   ↓
第二阶段        体验完善：历史页、编辑增强、选题
   ↓
第三阶段        真 Agent 架构：FastAPI + 多Agent + Web
```

### 8.2 第一阶段：MVP（打通核心闭环）⭐ 先做这个

目标：**现有功能不变，把三块引擎串成一条用户可见的完整流程。**

| # | 任务 | 交付物 | 验收标准 |
|---|------|--------|---------|
| 1 | **素材包模型化** `package.py` | 素材包读写/校验/版本 | 三个模块都通过它传数据 |
| 2 | **音乐模块接口化** | `recommend(analysis) → candidates` | 可独立调用，输入输出符合 6.2-B |
| 3 | **发布确认页** | 自检清单 + 审核按钮 + 执行日志 | 点「审核通过」→ 填充抖音 → 停在确认页 |
| 4 | **历史记录页** | 只读表格展示 xlsx | 列出所有记录，支持查看某期素材包 |
| 5 | **首页增强** | 最近记录卡片 + 开始引导 | 打开即知做什么 |
| 6 | **联调回归** | 全流程走一遍 | 与 V1.5 行为一致，不回归 |

> 原则：**先不改引擎，先加契约和页面。** 第一阶段结束时，应用从"能用"变成"流程完整"。

### 8.3 第二阶段：体验完善

| # | 任务 | 说明 |
|---|------|------|
| 1 | 历史页完整功能 | 筛选/搜索/回填到创作页、导出 |
| 2 | 结果页编辑增强 | 标题备选切换、标签批量编辑、图片重传 |
| 3 | 音乐区域增强 | 试听入口（本地曲库）、手动收藏曲目、自定义曲库 |
| 4 | 选题 Agent（轻量） | 从历史主题 + 账号定位推荐下周选题 |
| 5 | 发布数据回填 | 用户手动填回播放/点赞 → 历史页展示 |

### 8.4 第三阶段：真 Agent 架构

| # | 任务 | 说明 |
|---|------|------|

| 3 | 复盘 Agent | 自动分析发布数据 → 优化建议 |
| 4 | 数据库升级 | 数据量增大时迁 SQLite |

### 9.2 扩展清单

| 方向 | 优先级 | 依赖 |
|------|--------|------|
| 选题 Agent（推荐下周主题） | 高 | 历史记录数据 |
| 复盘 Agent（数据 → 优化建议） | 中 | 发布数据回填 |
| 数据可视化（粉丝画像/互动趋势） | 中 | SQLite + 图表 |
| 热点追踪 | 低 | 外部 API |
| 多平台发布（小红书/B站） | 低 | 各平台选择器映射 |
| 定时发布 | 低 | 抖音定时能力调研 |
| BGM 自动下载/填充 | 低 | 抖音 BGM 接口调研 |

### 9.3 扩展原则

- 每个新 Agent 都遵守同一契约：**输入 = 素材包或标准请求对象，输出 = 写回素材包或标准报告**
- 新增能力不修改已有引擎：内容生成、发布执行保持稳定
- 扩展优先级服从：**短期解决当前需求 → 中期提高质量 → 长期保证可扩展**
